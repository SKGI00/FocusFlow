## 4. System evaluation

I evaluated the FocusFlow prototype using two complementary approaches. ISO/IEC 25010:2023 provided a product-quality framework for selecting checks of functional suitability, reliability, interaction capability, security, maintainability and performance. PACMAD provided a mobile-user perspective, including effectiveness, efficiency, errors and cognitive load. I applied only those measures for which I could obtain genuine evidence, rather than treating a framework as proof of quality by itself.

For functional verification, I used Flutter automated tests, GitHub Actions and emulator-based tasks. At the recorded revision, all 58 automated tests passed, the analyser reported no issues and CI #6 succeeded. In a complete 15-minute study session, I checked countdown behaviour against the stopwatch on my phone. The timer reached completion and presented optional reflection as expected. I also confirmed one-tap distraction logging, pause/resume, continued operation after minimising, saved session history and persistence of the default-duration preference. The independent stopwatch check was qualitative: because I did not retain a numerical difference, I do not report a quantitative timing-accuracy percentage.

I applied three PACMAD task outcomes—starting focus, logging distraction and completing reflection/history. All three succeeded in one developer-performed session (3/3). This represents task completion under a familiar developer's conditions, not a population-level success rate. Exact task seconds, number of taps, satisfaction scores and cognitive-load ratings were not recorded, and memorability was not evaluated with a delayed retest. My familiarity with the app is likely to have made navigation easier than it would be for a first-time user.

The most useful quality finding came from accessibility testing. At enlarged text settings, the Reflection screen overflowed by six pixels and an Insights heading by two pixels. I modified both layouts and visually retested them; the reported overflow indicators disappeared. Offline checks also showed that session history and reflection survived app reopening. A separately configured 6:04 AM Android notification appeared at the scheduled time. These findings demonstrate strengths for the specific emulator, device settings and tested paths, but not universal accessibility, performance, security or iOS support.

Overall, these results support an operational offline-first Android prototype and a repeatable regression-testing approach. The main evaluation limitations are a single developer as tester, one Android emulator, absent independent timing/interaction metrics, no physical-device profiling and no iOS testing. I would improve subsequent iterations by recruiting consenting external users, running documented PACMAD tasks, testing TalkBack and physical devices, measuring performance objectively, and checking session-exit behaviour against user expectations.
